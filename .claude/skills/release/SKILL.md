# Release Checklist

Releases are cut by `.github/workflows/release.yml`: release-please keeps one release PR open on `main`; merging it tags `v<version>` and creates a draft GitHub Release; the `package` job builds the CI zip, deploys it to Freemius, checks the Free build Freemius generated, and only then attaches that Free build to the release as `post-quality-manager-<version>.zip` and publishes it (since 4.0.0, entry 8). The owner merges every release PR; agents never merge, tag or push to `main`.

1. Review the open release PR ("release <version>"): the header `Version`, `POSTQUALITY_VERSION`, `package.json` and `package-lock.json` all carry the proposed version; `POSTQUALITY_WORKFLOW_VERSION`, `Requires at least` and `Requires PHP` are untouched.
2. Check that `CHANGELOG.md` in the PR reflects the Conventional Commits merged since the last release.
3. Check the release notes on `main` (the `package` job appends `docs/release-notes/<version>.md`, when present, below the changelog in the release body). Stop before the merge and report it to the owner if `docs/release-notes/<version>.md` does not exist for the proposed version, or if `docs/release-notes/unreleased.md` still holds lines (it must be empty or gone). Report the gap; never fix it yourself. The fix is a separate `docs:` PR to `main`, opened once the release PR shows the version and merged before it (a `docs:` commit does not change the proposed version): it renames `unreleased.md` to `<version>.md`, or, with nothing silent to announce, adds a `<version>.md` saying there are no upgrade steps. After a rename, the next change that needs a line re-creates `unreleased.md`, starting with the `## Upgrading from an earlier version` heading.
4. The owner merges the release PR. Before that, run `/lcm` (ADR 0017) unless `memory/lifecycle.md` shows a check this month. The release PR runs no CI (release-please opens it with `GITHUB_TOKEN`), so `gh pr checks` shows the four checks `main` requires as missing or pending: that is expected, the owner merges release PRs past them as admin (owner, 2026-10-28), and it is not a blocker to report.
5. Watch the Release workflow on `main`: the `package` job builds from the tag and zips the full build (kept as a workflow artifact), runs steps 7 and 8 below, and only then attaches the Free build Freemius generated to the draft as `post-quality-manager-<version>.zip`, appends the release notes and publishes the release, shown as Latest (entry 8, ADR 0014 amended 2026-10-28). A red step anywhere leaves the release a draft with its tag and no zip: fix the cause and re-run the job; Freemius gets nothing twice, and the draft's body holds no notes yet, so they are appended once (`--clobber` replaces a zip a failed publish step left). If the publish step still fails, the owner can publish the draft by hand: attach the run's `post-quality-manager-<version>-free.zip` artifact (unzipped once) renamed `post-quality-manager-<version>.zip`, add the notes, and untick draft.
6. Download the zip from the published release, the Free build: its single root folder is `post-quality-manager/`, `admin/build/` is inside, and it installs and activates on a clean WordPress 6.6 showing the new version.
7. Freemius first (ADR 0014; details in `docs/distribution.md` § Release order): before publishing, the same `package` job deploys the CI zip to Freemius as an unreleased (pending) version, through the product API with the `FREEMIUS_API_TOKEN` secret (story 58). Read its log: the zip's sha256, then "Uploaded … as deployment <id>, release mode pending", or on a re-run of the newest release "Version <v> is already on Freemius as deployment <id>" (nothing is uploaded twice), and the Pro build's root folder. A red Freemius step leaves the GitHub Release a draft: read Freemius's error in the log, fix the cause (secret, Free plan, zip content), then re-run the job. A re-run of an older release already on Freemius stops on Freemius's refusal (`duplicate_plugin_version`) and uploads nothing: the job finds only the newest deployment (story 58, owner 2026-11-03), so a fix for an older release ships as a new version. Agents never upload by hand; the owner's manual upload (Deployment → Add New Version) is the fallback only when the job cannot run. Then read the PHP requirement Freemius recorded for this version (`requires_programming_language_version`, taken from `readme.txt`'s `Requires PHP`; the SDK hands it to WordPress's update gate for Pro updates; story 118, ADR 0018). The same step prints it at every release: "Freemius records Requires PHP <x> for <version>, as readme.txt says.", or a warning naming both values when they differ, or a warning that Freemius's reply carries none. Report it at every release; it decides only when `Requires PHP` differs from the previous release's (`git show v<previous>:post-quality-manager/readme.txt`): a different value → a bug ticket; no value in the reply → read the Deployment page's "Min PHP version" column, and file a bug ticket only when the column is empty or differs there too. A release whose run predates the line (3.13.1 and earlier) is read on that column (the owner's dashboard, for example through their Claude in Chrome with a read-only prompt); 3.13.0, the first release after the move to 8.1, read 8.1 there on 2026-11-09.
8. Before publishing, the job checks the Free build Freemius generated: no `__premium_only` outside `vendor/`, the header `Version` matches, its n8n template is `templates/n8n-workflow-free.json` alone, and it matches `bin/build-free.php`'s output: PHP as code through `bin/compare-php-trees.php` (Freemius re-prints every PHP file), everything else byte for byte. Both builds come back as artifacts `post-quality-manager-<version>-free.zip` and `-pro.zip` of the run; the Free one is the zip the release carries. On a red check the release stays a draft: report the log lines to the owner and stop; never fix a Freemius build by hand (the fix is a marker or the stripper in the source, then a new release, the next patch version). When the release that stays a draft was forced by `release-as` (4.0.0), the fix PR also removes `release-as` and `last-release-sha` and renames that version's notes file (`docs/release-notes/4.0.0.md`) to the next patch version's, or the next release PR proposes the same version again and the notes never reach a published release.
9. Once the WordPress.org listing exists (story 38), that Free artifact, the same build the GitHub Release carries, is what the SVN deploy pushes. Then the owner releases the version in Freemius (release mode Released) for licensed sites: the job uploads every version as pending, so a version stays unreleased until the owner sets it. "Release plans" has been ON since 2026-10-28 (`docs/distribution.md`) and holds no version back. The job never sets Released or Beta.

Versions follow the commits (`feat` → minor, `fix` → patch). To force a version, set `release-as` in `release-please-config.json` for that one release, and remove it as soon as the release is out.

Releases are public since 4.0.0. Before it, 3.0.0 to 3.13.3 were GitHub **pre-releases**, test builds none of which was shown as "Latest" (`"prerelease": true` in `release-please-config.json`, owner 2026-10-08; the publish step in `release.yml` still applies the key when set, because release-please alone ignores it for a non-suffixed version). The launch PR (entry 8, 2026-11-11) removed the key, set `release-as` to 4.0.0 (above the highest version already released, so installed test builds are offered the update) and `last-release-sha` to v3.13.3's commit (so the 4.0.0 changelog starts after it), and renamed `docs/release-notes/unreleased.md` to `4.0.0.md`. Remove `release-as` and `last-release-sha` as soon as 4.0.0 is out, or every release PR keeps proposing 4.0.0; since the launch, the rename follows step 3 (the release PR belongs to release-please). A published version number is never reused or re-tagged, even for a test build.

To check packaging without releasing, run the Release workflow by manual dispatch on any branch: it uploads the zip as a workflow artifact (unzip it once to get the upload file) and creates no tag and no release.
