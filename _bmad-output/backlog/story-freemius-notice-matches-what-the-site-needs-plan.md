## Intent

**Problem:** On a site the Freemius SDK treats as an update (any site that updated the plugin once, and every test-build site), activating the Pro build without a license makes the SDK add its sticky "We made a few tweaks to the plugin, Opt in to make "Post Quality Manager" better!". The site needs a license, and the link already opens the license screen (walk below, variants 1b and 3b): a buyer is asked to opt in.

**Approach:** On the Pro build, the plugin rewrites that notice's text as the SDK adds it, through the SDK's `sticky_message_connect_account` filter, so it asks for the license and keeps the SDK's own link. And the plugin clears the SDK's stored opt-in notice whenever the site is no longer waiting for an opt-in or a license (licensed, opted in or skipped), because the SDK leaves it after a license activation (owner, 2026-10-28). Every path the walk records as matching stays as it is (criterion 5).

## Boundaries & Constraints

**Always:** `vendor/freemius` unmodified; the text translatable in the plugin's text domain and escaped (the SDK stores and prints it as HTML); copy per `docs/brand.md`; the link is the SDK's activation URL; the Free build's notices unchanged. Approved copy: "Pro is installed. Enter your license key to unlock it." followed by the bold link "Activate your license".

**Never:** change the opt-in screen or what is sent to Freemius and when (ADR 0013 D8); reword other SDK strings ("W00t! Premium plugin version was successfully activated.", the license screen): story 62; hide or dismiss the notice instead of rewording it while the SDK still waits for an opt-in or a license.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Pro, update path, no license (1b, 3b) | the SDK adds `connect_account` | the license text, link = activation URL (license screen) | No error expected |
| Free, update path (path 1) | the SDK adds `connect_account` | the SDK's opt-in text, unchanged | No error expected |
| Pro, new install (path 3) | the SDK shows "Complete … Activation Now" | unchanged, the filter is not reached | No error expected |
| Free stored the opt-in notice, then Pro is activated (1b) | Free's deactivation clears `sticky_optin_added`, Pro re-adds the notice | the re-added notice carries the license text | if the walk after the build still shows the opt-in text, the Pro build clears the stored one (`remove_sticky()`), recorded in the Plan Change Log |
| Skipped, opted in (path 2), license activated | the SDK removes `connect_account`, or the plugin does when the SDK does not | no notice asks to opt in | a notice that survives in task 1's walk adds a matrix row before the build |
| Pro licensed on an already-registered site (2b, license activated) | `connect_account` stored, the SDK no longer in activation mode | the next admin page shows no notice asking to opt in or for a license | No error expected |
| Still waiting (either build, activation mode) | `connect_account` stored | the notice stays, as the rows above describe | No error expected |

## Design Notes

Why a filter and not the plugin's own notice: the SDK keeps owning the notice (its text slot, its dismiss and its link), and the plugin changes one string at the one place the SDK offers. The SDK never removes the notice on a license activation (seven removers, none of them there), so the plugin clears it once nothing is awaited, on both builds: outside activation mode the notice can only be a leftover. The text filter is Pro code and carries the build marker (AGENTS.md L47), so the Free build keeps the SDK's text by not containing the filter at all. The filter runs only when the SDK adds the notice: a notice stored by an earlier build on an unlicensed Pro site keeps its old words until Pro is deactivated and activated again or the license is activated (finding 1; only pre-launch test sites hold one). Skipped: the "W00t!" success notice on an unlicensed site, which misleads too: story 62 (SDK wording).
