# Walkthrough: PR #109, per-site webhook path (provisioning entry 3)

Target: PR #109 (commit a601c8e, branch feat/per-site-webhook-path). Current block: 1.

## [ ] 1. Intent — current

Changed during review: no

**Problem:** The template's Webhook Trigger listens on the static path `pqm-execute`, so two sites on one n8n instance, or a provisioned workflow beside a manual import, collide (spike finding 5); entry 4 needs a path the plugin computes per site, and the downloaded, imported and provisioned workflows must all carry the same one.

**Approach:** A `__PQM_WEBHOOK_PATH__` placeholder beside `__PQM_SITE_HOST__`, filled by `pqm_workflow_json()` from one new helper that later entries reuse; `PQM_WORKFLOW_VERSION` 5 → 6 stamped in its three places; the outdated-workflow copy tells a re-importing site that its production URL changes.

Source: the entry 6.3 plan's frozen Intent ([plan](../epic-n8n-provisioning/story-the-workflow-template-carries-a-per-site-webhook-path-plan.md)). Owner decisions at the plan: a readable host slug, not a hash; re-importing sites are told by copy only, the saved URL is not migrated.

## [ ] 3. Slice: the path and its fill — not visited

Changed during review: no

`pqm_webhook_path()` lower-cases `pqm_site_host()`, turns every run of characters outside a–z and 0–9 into one dash and trims dashes, behind the prefix `pqm-execute-`. It uses plain PHP, no filterable WordPress function, so download, import URL and later provisioning agree. `pqm_workflow_json()` fills both placeholders in one `str_replace`. Known ceiling, named in the docblock: two installs on one host share the path.
