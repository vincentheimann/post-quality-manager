Decided 2026-09-22 (ADR [0003](../docs/adr/0003-freemium-plan-and-role-based-access.md)), **ranked first by `/prioritize` and incepted 2026-10-01** — requirement ids CAP-1…CAP-5 live in `_bmad-output/initiative-post-quality-manager/spec-freemium-and-roles/` (kernel + access-matrix.md companion):

- **Tiers:** free = Review + Key Takeaways; paid = all agents, per-agent overrides, cron, role management. Licensing via Freemius (provider-agnostic `is_pro()` source). Paid plan licensed per site. **Two builds from one source since 2026-10-09 (ADR [0014](../docs/adr/0014-two-builds-from-one-source.md), replaces ADR 0003's "one zip" and "one n8n template"):** WordPress.org guideline 5 forbids locked functionality in a directory plugin, so the Free build (Freemius strips the `__premium_only`-marked code and ships a template without the paid branches) is what the directory hosts and the Pro build (everything, license-gated at runtime) is what Freemius serves; the Free build is a complete product with one "Get Pro" section and nothing greyed out; the Pro code stays public and GPL. Runtime gate, `why_not()`, caps, quota and carry rules unchanged; the locked-section presentation survives only in the Pro build for a lapsed license. Backlog story 54 does the marking, the Free template, the handshake variant and the CI check on the Free build; it sits between story 44 (SDK) and story 38 (listing).
- **Roles:** Administrator full · Editor = Author + the four paid agents + per-agent overrides + cron (decided 2026-10-01) · Author = Review + Key Takeaways with a per-user monthly quota (Admin-configured, default 20; decided 2026-10-01) · Contributor nothing. Implemented as plugin capabilities registered on activation, enforced in REST + AJAX.
- **Capabilities (built, story 2, 2026-10-01):** five `pqm_` caps (`postquality_` since story 91, 2026-10-26, moved by a one-time upgrade), map + register/remove in `PostQuality_Features::capabilities()` — `postquality_view_reviews` (Admin, Editor, Author: Dashboard, Post Reviews menus, `GET /reviews`, `GET /post-score`) · `postquality_run_free_agents` (Admin, Editor, Author: review, takeaways, score, apply — explicit free-tier registry entries since ticket 14; also the WP-auth path of `/save-review`) · `postquality_run_paid_agents` (Admin, Editor: rewrite, sources, seo, audit) · `postquality_manage_agents` (Admin, Editor: the Settings page + its save since story 5, i.e. the overrides + Automated Reviews sections) · `postquality_manage_settings` (Admin: n8n Workflow menu, the Settings page's admin-only sections, workflow download, webhook save, ping, cron nudge, WP-auth path of `GET /workflow`). Contributor holds none. No `edit_posts` check remains in the plugin and core `manage_options` gates only the Roles tab (story 42); the Roles tab or a role editor remaps everything with no code change.
- **Registration & upgrade:** `PostQuality_Activator::activate()` grants the default map via `WP_Role::add_cap()` and stores `postquality_caps_version` = `PostQuality_Features::CAPS_VERSION`; `PostQuality_Activator::maybe_upgrade()` on `init` re-registers when the stored version is behind (zip-replaced installs are never locked out; bump `CAPS_VERSION` whenever `capabilities()` changes). No `remove_cap` on deactivation — only uninstall strips the caps (`PostQuality_Activator::uninstall()`, run by the Freemius SDK's `after_uninstall` hook since story 44; `uninstall.php` is gone because WordPress would run it instead of the SDK's hook) (`PostQuality_Features::remove_capabilities()`: every role, then every user's direct grants via `get_users( capability__in )`, bug 20 fixed 2026-10-06) and deletes the option. Since story 42 registration grants a capability's defaults only while no `manage_options` role holds it, so reactivation and upgrades no longer bring back a cap removed from a role (Roles tab or role editor) — see the Roles tab bullet. **The current user on the upgrade request (bug 94, fixed 2026-10-28; read on WordPress 7.1.3 the same day):** WordPress loads the current user in `WP::init()` before it fires `init` (`wp-settings.php` L766, L779), so a capability change on `init` reaches that user only after `WP_User::for_site()` (`class-wp-user.php` L873: re-reads the user's own capabilities meta and re-merges the role grants; `WP_Role::add_cap()` has already updated the in-memory role); `wp_set_current_user()` would not do it, it returns early for the same user ID. Hence `maybe_upgrade()` calls `wp_get_current_user()->for_site()` once when the names migration or the caps grant ran, never on a finished site (user 0 on cron and WP-CLI: nothing loaded, nothing written). Before that, an administrator's first page after an update from a `pqm_` build (Dashboard, Post Reviews, n8n Workflow) answered "Sorry, you are not allowed to access this page." Harnesses: `stored-names-harness.php` Row 7, `caps-harness.php` Row 8.
- **Hidden vs locked:** `PostQuality_Features::why_not( $command )` returns `'role'` (lacks the cap) before `'plan'` (paid tier, unlicensed) — nothing to upsell to a role that cannot run the agent. REST answers 403 `pqm_feature_gated` with role copy ("%s is not available for your role. Ask an administrator to extend it.") or the upgrade copy. The React pages read the split from the `GET /posts` `viewer` block: `hidden_commands` (`hidden_commands()`, buttons not rendered) and `gated_commands` (`gated_commands()`, visible-but-locked) are disjoint. `POST /trigger-review` is the one trigger path, gated by `PostQuality_REST_API::check_can_trigger()` (any registry cap) at the route; the exact per-command decision stays in `trigger_review_callback()` (legacy AJAX/GET paths and the `postqualityAdmin` gate keys removed in story 5.7).

Uninstall: `PostQuality_Activator::uninstall()` hooked to the SDK's `after_uninstall` (the SDK registers its uninstall hook on deactivation, opted in or not), `uninstall.php` deleted. - **Gate:** single `PostQuality_Features::can()` combining plan + capability. The plugin refuses gated commands before the webhook (the Free build ships its own template since story 54). **Built (story 1.1, 2026-10-01):** `includes/class-pqm-features.php` — `registry()` (six agents + `score` / `apply` as free-tier entries since ticket 14, 2026-10-06; tiers per the access matrix, capabilities `postquality_run_free_agents` / `postquality_run_paid_agents` since story 2), `is_pro()` delegating to `PostQuality_License` since story 3, one gate call in `PostQuality_REST_API::trigger_review_callback()` on `POST /trigger-review`, the one trigger path (legacy AJAX/GET paths removed in story 5.7); paid buttons render visible-but-locked from the `GET /posts` `viewer.gated_commands`. **The registry is the one command whitelist (ticket 14, 2026-10-06):** the `command` enums of `/trigger-review` and `/save-review` are `array_keys( PostQuality_Features::registry() )` (WP answers 400 `rest_invalid_param` to anything else, before any webhook), and `why_not()` / `plan_allows()` fail closed — an unknown command is `'role'` / `false` for every caller, cron and direct calls included. `apply_*` have no entry (their AJAX/GET paths died in story 5.7) and are refused; `ping` never goes through the gate. Adding a command = a registry entry + the n8n template's `validCommands` (Parse Input node) and a Route Command branch; `caps-harness.php` + `rest-posts-harness.php` fail when the registry, the REST enums and the template's `validCommands` drift apart. **Cron is gated site-level (story 6, 2026-10-02):** `PostQuality_Features::plan_allows( $command )` is the plan half of the gate alone (free tier or `is_pro()`; unknown commands refused since ticket 14, like `why_not()` — whose plan branch now delegates to it, so licensing keeps touching only `is_pro()`); `PostQuality_Cron::run_scheduled_review()` checks it once per batch and silently skips — no fallback to `review`, no DB query, no webhook — when the stored `cron_command` is plan-gated (e.g. after a license lapse). Cron has no user, so the role half never applies, and it stays quota-free (locked in by `tests/harness/cron-gate-harness.php`). **Schedulable commands (ticket 3, 2026-10-06):** `PostQuality_Admin::cron_commands__premium_only()` = review, seo, audit — one per schedule, an enabled select labelled via `PostQuality_Features::label()`; the pro sanitizer path keeps a posted one of those, else `review` (rewrite never; the carry rules above unchanged, `cron_command` is not a "section posted" knob). `PostQuality_DB::get_posts_needing_review( …, $command = 'review' )` picks posts by their latest row of that command (prepared `%s` in the subquery and the r1 join). The dashboard tiles, chip counts and trend stay review-only; scheduled seo/audit results show in the post's tab and row chips.

- **Author quota (built, story 4, 2026-10-01; spec CAP-4):** per user, per calendar month (site timezone), for anyone *without* `postquality_run_paid_agents` — `PostQuality_Features::is_quota_subject()`; granting paid agents lifts the quota, no new capability, `CAPS_VERSION` unchanged.
