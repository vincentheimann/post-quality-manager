Decided 2026-09-22 (ADR [0003](../docs/adr/0003-freemium-plan-and-role-based-access.md)), **ranked first by `/prioritize` and incepted 2026-10-01** — requirement ids CAP-1…CAP-5 live in `_bmad-output/initiative-post-quality-manager/spec-freemium-and-roles/` (kernel + access-matrix.md companion):

- **Tiers:** free = Review + Key Takeaways; paid = all agents, per-agent overrides, cron, role management. One zip, license key flips the gate. Licensing via Freemius (provider-agnostic `is_pro()` source). Paid plan licensed per site.
- **Roles:** Administrator full · Editor = Author + the four paid agents + per-agent overrides + cron (decided 2026-10-01) · Author = Review + Key Takeaways with a per-user monthly quota (Admin-configured, default 20; decided 2026-10-01) · Contributor nothing. Implemented as plugin capabilities registered on activation, enforced in REST + AJAX.
- **Capabilities (built, story 2, 2026-10-01):** five `pqm_` caps, map + register/remove in `PQM_Features::capabilities()` — `pqm_view_reviews` (Admin, Editor, Author: Dashboard, Post Reviews menus, `GET /reviews`, `GET /post-score`) · `pqm_run_free_agents` (Admin, Editor, Author: review, takeaways, score, apply — explicit free-tier registry entries since ticket 14; also the WP-auth path of `/save-review`) · `pqm_run_paid_agents` (Admin, Editor: rewrite, sources, seo, audit) · `pqm_manage_agents` (Admin, Editor: the Settings page + its save since story 5, i.e. the overrides + Automated Reviews sections) · `pqm_manage_settings` (Admin: n8n Workflow menu, the Settings page's admin-only sections, workflow download, webhook save, ping, cron nudge, WP-auth path of `GET /workflow`). Contributor holds none. No `edit_posts` check remains in the plugin and core `manage_options` gates only the Roles tab (story 42); the Roles tab or a role editor remaps everything with no code change.
- **Registration & upgrade:** `PQM_Activator::activate()` grants the default map via `WP_Role::add_cap()` and stores `pqm_caps_version` = `PQM_Features::CAPS_VERSION`; `PQM_Activator::maybe_upgrade()` on `init` re-registers when the stored version is behind (zip-replaced installs are never locked out; bump `CAPS_VERSION` whenever `capabilities()` changes). No `remove_cap` on deactivation — only `uninstall.php` strips the caps (`PQM_Features::remove_capabilities()`: every role, then every user's direct grants via `get_users( capability__in )`, bug 20 fixed 2026-10-06) and deletes the option. Since story 42 registration grants a capability's defaults only while no `manage_options` role holds it, so reactivation and upgrades no longer bring back a cap removed from a role (Roles tab or role editor) — see the Roles tab bullet.
- **Hidden vs locked:** `PQM_Features::why_not( $command )` returns `'role'` (lacks the cap) before `'plan'` (paid tier, unlicensed) — nothing to upsell to a role that cannot run the agent. REST answers 403 `pqm_feature_gated` with role copy ("%s is not available for your role. Ask an administrator to extend it.") or the upgrade copy. The React pages read the split from the `GET /posts` `viewer` block: `hidden_commands` (`hidden_commands()`, buttons not rendered) and `gated_commands` (`gated_commands()`, visible-but-locked) are disjoint. `POST /trigger-review` is the one trigger path, gated by `PQM_REST_API::check_can_trigger()` (any registry cap) at the route; the exact per-command decision stays in `trigger_review_callback()` (legacy AJAX/GET paths and the `pqmAdmin` gate keys removed in story 5.7).
- **License provider (built, story 3, 2026-10-02; spec CAP-2):** `includes/class-pqm-license.php` — all-static `PQM_License`, the one confined, swappable provider; `PQM_Features::is_pro()` is now `apply_filters( 'pqm_is_pro', PQM_License::is_pro() )`, so the mu-plugin dev override still always wins and gate callers / `why_not()` / `plan_allows()` are untouched. **Stub validity (owner, 2026-10-02): any non-empty key = pro** — `is_pro()` = stored `license_key` (inside `pqm_settings`, default `''`, no new option) trimmed non-empty, read per call (no caching/transients; option reads are request-cached and save is the commit point). Key entry: admin-only "License" section first on the Settings page (role-hidden via `pqm_manage_settings`, plain Free/Pro status line), sanitized `trim( sanitize_text_field() )` in the admin branch and on the `$admin_only_keys` carry list — non-admin saves keep the stored key byte-identical. Real Freemius (SDK, owner creates the product, release-notes/migration for installs the flip turns free) is deferred to the end of the epic — `_bmad-output/initiative-post-quality-manager/deferred-work.md`; it replaces only `PQM_License`'s internals. **Commercial model decided 2026-10-09 (ADR [0013](../docs/adr/0013-pro-sold-through-freemius-before-public-release.md), spike 43):** Freemius, one yearly Pro plan in 1 / 5 / unlimited site packs, USD and EUR, 14-day money-back, lapse to Free keeping stored settings; real licensing (backlog story 44) lands before the first public release (entry 4.8), so the stub never ships publicly. Seller: the owner as a private person; prices 49 / 99 / 199 a year (1 / 5 / unlimited sites); support hello@postquality.com within 2 business days; domain postquality.com. Locked in by `tests/harness/license-harness.php` + the sanitize matrix.
- **Presentation** (decided 2026-10-01): plan-gated features visible but locked with upgrade copy; role-gated features hidden.
- **Gate:** single `PQM_Features::can()` combining plan + capability. One n8n template; the plugin refuses gated commands before the webhook. **Built (story 1.1, 2026-10-01):** `includes/class-pqm-features.php` — `registry()` (six agents + `score` / `apply` as free-tier entries since ticket 14, 2026-10-06; tiers per the access matrix, capabilities `pqm_run_free_agents` / `pqm_run_paid_agents` since story 2), `is_pro()` delegating to `PQM_License` since story 3, one gate call in `PQM_REST_API::trigger_review_callback()` on `POST /trigger-review`, the one trigger path (legacy AJAX/GET paths removed in story 5.7); paid buttons render visible-but-locked from the `GET /posts` `viewer.gated_commands`. **The registry is the one command whitelist (ticket 14, 2026-10-06):** the `command` enums of `/trigger-review` and `/save-review` are `array_keys( PQM_Features::registry() )` (WP answers 400 `rest_invalid_param` to anything else, before any webhook), and `why_not()` / `plan_allows()` fail closed — an unknown command is `'role'` / `false` for every caller, cron and direct calls included. `apply_*` have no entry (their AJAX/GET paths died in story 5.7) and are refused; `ping` never goes through the gate. Adding a command = a registry entry + the n8n template's `validCommands` (Parse Input node) and a Route Command branch; `caps-harness.php` + `rest-posts-harness.php` fail when the registry, the REST enums and the template's `validCommands` drift apart. **Cron is gated site-level (story 6, 2026-10-02):** `PQM_Features::plan_allows( $command )` is the plan half of the gate alone (free tier or `is_pro()`; unknown commands refused since ticket 14, like `why_not()` — whose plan branch now delegates to it, so licensing keeps touching only `is_pro()`); `PQM_Cron::run_scheduled_review()` checks it once per batch and silently skips — no fallback to `review`, no DB query, no webhook — when the stored `cron_command` is plan-gated (e.g. after a license lapse). Cron has no user, so the role half never applies, and it stays quota-free (locked in by `tests/harness/cron-gate-harness.php`). **Schedulable commands (ticket 3, 2026-10-06):** `PQM_Admin::CRON_COMMANDS` = review, seo, audit — one per schedule, an enabled select labelled via `PQM_Features::label()`; the pro sanitizer path keeps a posted one of those, else `review` (rewrite never; the carry rules above unchanged, `cron_command` is not a "section posted" knob). `PQM_DB::get_posts_needing_review( …, $command = 'review' )` picks posts by their latest row of that command (prepared `%s` in the subquery and the r1 join). The dashboard tiles, chip counts and trend stay review-only; scheduled seo/audit results show in the post's tab and row chips.
- **Command labels (story 11, 2026-10-06):** each `PQM_Features::registry()` entry carries a translated `label`, read via `PQM_Features::label( $command )` (raw key when unknown); REST copy uses it and `enqueue_app()` ships the map to JS as `window.pqmCommandLabels`, which `src/kit/copy.js` `commandLabel()` reads — no label lives in JS.
- **Author quota (built, story 4, 2026-10-01; spec CAP-4):** per user, per calendar month (site timezone), for anyone *without* `pqm_run_paid_agents` — `PQM_Features::is_quota_subject()`; granting paid agents lifts the quota, no new capability, `CAPS_VERSION` unchanged. Storage is one self-resetting user meta `pqm_monthly_usage` = `['month' => 'YYYY-MM', 'count' => N]` (schema unknown resolved 2026-10-01: user meta, no usage table): a stale month reads as 0 and is overwritten on the next increment, so there is no reset cron. Setting `author_quota` (shipped default 20; Settings → "Monthly Quota", Admin-only via `pqm_manage_settings`, `absint`-sanitized; **0 = unlimited** escape hatch → `quota_state()` returns null, same as exempt). Enforced only in `PQM_REST_API::trigger_review_callback()` — the single chokepoint behind `POST /trigger-review`, the one trigger path (legacy AJAX/GET paths removed in story 5.7) — *after* the feature gate, so role/plan refusals keep priority: `pqm_quota_exceeded` 429 with count + reset-date copy. `consume_quota()` runs only after the n8n webhook answers 2xx: refusals, unreachable n8n and non-2xx answers never spend an action; `score` / `apply` (free-tier registry entries) consume too. Cron (`PQM_Cron`) posts to n8n directly and never enters the callback → quota-free by construction. UI: the `GET /posts` `viewer.quota` (= `quota_state()`: `limit`/`used`/`remaining`/`resets`, null when exempt/unlimited) feeds the kit's `QuotaNote` (`.pqm-quota-note`, "%1$d of %2$d AI actions left this month") in the Post Reviews filter bar and next to the detail panel's action buttons; the list refetch after each trigger keeps it current (the PHP span and JS `quotaNote()` were removed in story 5.7). `uninstall.php` deletes the meta for all users via `delete_metadata('user', 0, …, true)`.
- **Settings sections (built, story 5, 2026-10-01; spec CAP-3):** the Settings page and `option_page_capability_pqm_settings_group` both resolve through `PQM_Admin::settings_page_capability()` — `pqm_manage_settings` when the user holds it, else `pqm_manage_agents` when held, else core `manage_options` (story 42, so an Administrator whose role lost both plugin caps still reaches the Roles tab) — so either cap opens and saves the page (Admin + Editor by default); sections follow the access matrix — n8n Connection, AI Model, AI Prompts & Context and Monthly Quota are *hidden* without `pqm_manage_settings`; Agent-Specific Overrides and Automated Reviews are *hidden* without `pqm_manage_agents` (ticket 16, 2026-10-06: a role remapped to `pqm_manage_settings` alone still reaches the page via `settings_page_capability()`, but sees only the admin sections; the Dashboard cron nudge (`GET /dashboard` `cron_nudge`, pro only) and its dismiss handler in `render_dashboard_app()` follow `pqm_manage_agents` too, while the response's `can_manage_settings` stays the settings cap) and *plan-locked* (visible, upgrade copy, wrapped in one `<fieldset disabled class="pqm-locked-section">` — JS-proof, nothing inside POSTs) when `is_pro()` is false, for Admins too. Role-hidden beats plan-locked. **Sanitizer carry rule** (`sanitize_settings()`): section-wise, never per-field — admin-only keys (`n8n_webhook_url`, `webhook_token`, `notification_url`, `blog_profile`, `brand_voice_preset`, `brand_voice`, `website_context`, `default_model`, `custom_model`, `author_quota`) come from `$input` only when the saver has `pqm_manage_settings`, else from the *stored* settings; `cron_*` + `agent_prompts` come from `$input` only when the saver has `pqm_manage_agents` (ticket 16), the site is pro *and* the request posted the section (any cron key; per agent for overrides), else carried wholesale from stored (so a locked `cron_enabled = true` survives the absent checkbox, and a pro-site save from a form rendered while free or a direct POST wipes nothing, bug 19 fixed 2026-10-06; the per-knob stored fallback for model-locked temperature/effort stays on the pro path). **The one exception, the free-site off-switch (ticket 13, 2026-10-06):** on a free site whose stored `cron_enabled` is true and whose stored `cron_command` passes `plan_allows()` (ticket 3: a paid seo/audit schedule is skipped by cron, so its section stays fully locked with the normal note), the Enable toggle renders *outside* the locked fieldset (hidden `cron_enabled = 0` before the checkbox, plus a "can be switched off but not back on" line, and a locked note saying the scheduled reviews keep running) for anyone who sees the section (`pqm_manage_agents`), and the carry branch reads `$input['cron_enabled']` only to switch off: stored true + posted empty → false, `PQM_Cron::schedule()` clears the event. The exception is plan-independent (a stale off-switch form saved after the site turned pro still switches off), and "cron section posted" on the pro path means the knobs the pro form always posts (`cron_frequency`, `cron_batch_size`, `cron_min_score`, `cron_max_age_days`), never `cron_enabled` / `cron_command` — so that stale form cannot reset the knobs to defaults. The carry branch never sets it true; every other cron key still carries; with stored false the section stays fully locked. **Tabs (story 27, 2026-10-08):** the sections sit under native `nav-tab` tabs over the *one* form — Connection (License, n8n Connection), AI (AI Model, AI Prompts & Context, Agent-Specific Overrides), Automation (Automated Reviews), Usage & Limits (Monthly Quota), and since story 42 a fifth, Roles, last, for core `manage_options` holders only; each panel is `div.pqm-tab-panel#pqm-panel-<slug>` (`connection`/`ai`/`automation`/`usage`/`roles`), a tab renders only when one of its sections does (Editor: AI with Overrides only + Automation; settings-only: Connection, AI, Usage & Limits), the server marks the first active. `initSettingsTabs()` in `pqm-admin.js` switches them (ARIA tablist, roving tabindex, Left/Right/Home/End), keeps the active tab in the hash `#tab-<slug>` and in `_wp_http_referer` so a save returns to it, resolves the section anchors `#pqm-context-settings` / `#pqm-cron-settings` / `#pqm-quota-settings` to their panel, and opens the panel of a field the browser rejects on submit. An inline script under the tab bar adds `pqm-tabs-pending` to `<html>` when the hash names another tab than the first, hiding every panel until the footer JS opens the right one (no flash of the first panel). JS off (`.no-js`): no tab bar, every section shows. The tab JS is covered by `tests/js/settings-tabs.test.js` (Jest + jsdom, `npm run test:unit`, also in CI). Every save still posts every section — sanitizer and option shape unchanged (render + sanitize matrices lock it in). JS: every settings block guards on its own elements; `pqmAdmin.defaultModel` (effective global default, Custom resolved) feeds the model-caps refresh when the AI Model section is absent. n8n Workflow page stays `pqm_manage_settings`. **README truth (ticket 16):** the README's "Admin pages & capabilities" carries a *Capability | Default roles* table that `caps-harness.php` Row 7 parses and asserts equal to `capabilities()` (edit both together), and states single-site only — multisite is unsupported because the `pqm_monthly_usage` quota counter is network-wide user meta while `author_quota` is a per-site setting.
- **Roles tab (built, backlog story 42, 2026-10-08; ADR [0012](../docs/adr/0012-role-rights-set-in-the-plugin-view-as-retired.md); spec CAP-6):** fifth Settings tab "Roles" (`#pqm-panel-roles`, last after Usage & Limits), rendered for core `manage_options` holders only (never a `pqm_` cap, so the tab cannot remove itself). Headline "What each role can do"; a `widefat` table with one row per `wp_roles()->role_objects` entry (display name via `translate_user_role()`, custom roles included) and one checkbox per `capabilities()` key under the plain labels of `PQM_Admin::role_cap_labels()` (View reviews · Run Review and Key Takeaways · Run paid agents · Manage agents · Manage settings), `pqm_settings[roles][<role>][]=<cap>`; no `pqm_` slug in visible text. Rows of roles holding `manage_options` are disabled (capability-keyed): all-checked on Pro, the role's current grants on Free like every other row. A hidden `pqm_settings[roles_posted]` marker tells "tab posted with every box cleared" from "not posted"; each unpinned row also posts a hidden `pqm_settings[roles_shown][<role>]` = the caps it rendered checked, comma-separated (none for a pinned row, so a role that loses `manage_options` before Save is skipped). `settings_page_capability()` falls back to core `manage_options` when the user holds neither plugin cap, so the tab is never behind a plugin capability. Copy (no "rights" or `manage_options` wording on screen): intro "Saving applies these choices to every user with that role. Locked rows belong to roles that run the whole site, such as Administrator: you cannot take anything away from them."; CSS-only hint `.pqm-role-hint` ("Without this, the role does not see Dashboard or Post Reviews.") after each View reviews box, linked by `aria-describedby`, shown while it is unchecked; a note under the table that Run paid agents lifts the monthly quota. Pro only: on a free site the table sits in the locked pattern (lock icon, `pqm-locked-note` "Available with Pro. Upgrade to choose what each role can do — until then, every role keeps what is shown here.", `<fieldset disabled class="pqm-locked-section">`, marker and `roles_shown` inside so nothing posts). **Save:** the site's roles are the only store (plan decision B) — `sanitize_settings()` calls `PQM_Admin::save_roles()` only when the saver holds `manage_options`, `is_pro()` and the marker was posted (absent for anyone without the tab, inside the free lock and from programmatic `update_option()`, e.g. the setup dialog); `manage_options` roles get all five whatever was posted; every other role is written only for the cells whose posted box differs from its `roles_shown` (review loop 1: the panel is in the one form, so every pro Administrator save posts it from any tab — writing the posted state would undo a role-editor change made after the page loaded), and a role with no `roles_shown` entry (created since, or forged) is never touched. A cell whose role already matches gets no `add_cap`/`remove_cap` (idempotent, so the double sanitize on a first save is harmless), only the five caps on roles are touched (never core caps, never per-user grants), and none of `roles`, `roles_shown`, `roles_posted` is stored in `pqm_settings`. A lapsed license reverts nothing. **Registration:** `PQM_Features::register_capabilities()` grants a capability's defaults only while no `manage_options` role holds it (fresh install, or a cap new in a `CAPS_VERSION`), so activation and `maybe_upgrade()` never reset a role set on the tab; ceiling: a role editor stripping a cap from every `manage_options` role makes the next activation grant its defaults again. Locked in by `caps-harness.php` Rows 8–10, `sanitize-matrix-harness.php` Case 15 and the render matrix's Roles rows. **View as (story 34) is retired:** class, toolbar nodes, `admin_post_pqm_view_as` handler, `user_has_cap` filter and `view-as-harness.php` are gone; a stored `pqm_view_as` meta has no effect and `uninstall.php` still deletes it for one release (caps-harness Row 10 checks only View as identifiers — `PQM_View_As`, `class-pqm-view-as`, `filter_caps`, the switch action — never generic hook names). Release notes (story 15) must name the removal.
