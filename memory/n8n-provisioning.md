# n8n provisioning

Decided 2026-10-12 (ADR 0015, from spike 56): the setup wizard will provision n8n through its public API — create the three credentials, create/activate the workflow with per-node credential ids, compute the webhook URL, verify with ping. Template updates become `PUT /workflows/{id}` (auto-republish, ends the re-import handshake), token rotation becomes `PATCH /credentials/{id}`. Not built yet. **Spec written 2026-10-13** (`_bmad-output/initiative-post-quality-manager/spec-n8n-provisioning/`: kernel CAP-1..8, `failure-modes.md`, `brownfield.md`, the spike findings adopted as companion): one epic — connect by key, fresh provisioning, rollback, adopt-existing, one-click template update, token rotation, mis-wiring diagnosis (new: on 2026-10-13 the owner's production n8n had the one Header Auth credential auto-assigned to all seven nodes on import, so every AI call failed silently), manual fallback absorbing story 40. **Epic incepted 2026-10-13** as `epic-n8n-provisioning` (initiative epic 6, covers UV4, 12 entries in `tickets.toml`): 1 connect by key (tracer, hitl probe), 2 manual fallback (absorbs story 40, dropped by reference), 3 per-site webhook path (the epic's one `PQM_WORKFLOW_VERSION` bump, to 6), 4 server provisioning, 5 rollback, 6 the wizard (exposes provisioning only after rollback), 7 mis-wiring diagnosis (hitl: the owner's production workflow), 8 adopt, 9 one-click template update, 10 token rotation, 11 refactor sweep, 12 success-signal walk + records. Owner decisions at inception: the manual path is open by choice (the wizard leads with the key, "Set up by hand instead" secondary); policy wording ships with the story that makes it true (entries 1 and 6); CAP-7 finds a manual workflow by the saved webhook URL's path, read-only; the n8n URL and key get their own option, not `pqm_settings`; rollback also revokes the generated Application Password.

- **Provider-key rule (entry 4):** the Anthropic key is used in two places only — the models request and the Anthropic credential body. It is never stored in an option, never put in a REST reply or an error message, never logged; n8n's reply bodies are not repeated in errors (they may quote the request). `n8n-api-harness.php` scans every option, reply, ping and outgoing call for it.

- The n8n API key will be **stored** in settings (owner accepted the blast radius; mitigations: dedicated expiring key, Forget button, HTTPS-only base URL, plugin-identifying `User-Agent` — generic agents get WAF-banned).
- The provider key passes through the plugin **once** during setup: validated by a direct provider call (n8n's credential test is a no-op for generic types), written to the n8n credential, never stored. ADR 0009 stands; `docs/policies/` say "forwarded once, never stored" since entry 6.
- Adopt-existing lists credentials (metadata only, never secrets) and asks the owner to confirm; deterministic names are trusted only for wizard-created setups.
- The webhook path is per-site since entry 3 (template v6): `pqm_webhook_path()` (`includes/pqm-functions.php`) = `pqm-execute-<host-slug>` (e.g. `pqm-execute-example-com`), the one derivation every entry reuses; see the entry 3 line above.
- n8n's UI words and credential behaviour are verified against n8n's own source at the tested tag (`n8n@2.42.3`: `packages/frontend/@n8n/i18n/src/locales/en.json` for labels, the `editor-ui` components for where they sit), not the docs; checked 2026-10-14 for entry 2. The workflow menu is "Import" → "From URL" / "From file"; credentials are created from the arrow beside "Create workflow" on the Overview page ("Create credential"); the chevron beside "Publish" holds "Unpublish". Credential filling: an import drops the template's credentials (names without ids) and gives non-HTTP-Request nodes (the Webhook Trigger) the most recently saved credential of their type; opening a node fills an empty one the same way; a credential picked by hand is added to every other empty node accepting that type ("Added this credential to N other node(s)"). So a webhook credential picked first spreads to all Claude nodes, the likely path of the 2026-10-13 mis-wiring; the Workflow File section has the Claude nodes done first.
- The manual import path remains the fallback: Cloud trial, disabled API, older n8n. Everything is confirmed on 2.42.3 only; the wizard probes and degrades.
- Rollback order on failed provisioning (built in entry 5): deactivate → delete workflow → delete credentials, no credential before the workflow delete passed (published or still-unpublishing workflows refuse DELETE with 409; credentials delete silently even while referenced).

Product decisions for the spec (owner-delegated, 2026-10-12):

- Provisioning is a **free** feature: UV4 is the evaluation funnel, Pro sells outcomes (ADR 0003), the manual path is the fallback, not the free tier.
- Adopt vs fresh: a connected site with a green handshake defaults to "keep existing" (key stored for future updates, credential mapping only with explicit confirmation); an unconfigured site defaults to fresh provisioning; nothing manual is ever auto-deleted.
- The n8n API key lives on the **n8n Workflow page** (page-local merge-save, write-only masked field, "set / not set" + Forget) — never in the Settings form, which re-echoes values.
- Sequencing: story 55 (wizard continuation) builds first; the provisioning epic reworks the n8n connection steps afterwards and absorbs story 40 as the manual-fallback story.
