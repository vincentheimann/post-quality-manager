# LLM options architecture (since 2026-07-23)

Modern Claude models removed/restricted `temperature` (Opus 4.7+ rejects it with HTTP 400; Sonnet 5 rejects non-default values), so the plugin pivoted from "temperature everywhere" to a registry-driven design. Three layers, all in the plugin — the n8n workflow is a dumb executor:

1. **Model registry** — `postquality_model_registry()` in `includes/pqm-functions.php` (every `postquality_*` helper moved there from the main file in story 54, 2026-10-12) is the single source of truth for which request parameters each model accepts (`supports_temperature`, `effort_levels`, `thinking`). Settings UI, sanitizer, admin JS (`postqualityAdmin.modelRegistry`), and the param builder all consume it. Supporting a new model = one registry entry.
2. **Param builder** — `postquality_llm_params($agent, $settings)` returns the ready-to-merge Claude request fragment (`model`, `max_tokens`, plus only the knobs the model supports). `postquality_n8n_payload()` (shared by REST trigger + cron) ships a per-agent `llm` map in every webhook payload.
3. **Workflow spreads, never decides** — the six "Build … Body" Code nodes do `{ ...d.llm[agent], system, messages }`; the six parse nodes read the first `text` content block (`find(b => b.type === 'text')`, thinking-proof). LLM option changes therefore **never require a workflow re-import**.

Key decisions (user, 2026-07-23): per-agent model selects with a global default + "inherit"; temperature kept where the model supports it (since 2026-07-24: slider stays visible but *locked* — `disabled` + dimmed + hint — instead of hidden; same for the effort select; because disabled inputs don't POST, `sanitize_settings()` falls back to the stored value, not the default); default model `claude-sonnet-4-6` (no silent behavior change); Custom free-text model ID at the global level only (conservative params: model + max_tokens only). Sonnet 5 gets `thinking: {type: "disabled"}` so adaptive thinking doesn't eat the agents' small output budgets.

**Decided, not built (ADR 0009, 2026-10-06):** several providers — Anthropic, OpenAI, Google, OpenRouter for free models — through two request shapes (Anthropic Messages + OpenAI Chat Completions); the registry gains a provider per model; the default becomes `claude-sonnet-5-5`; keys stay in n8n credentials; one site-wide monthly token limit from provider-reported usage. Layers 1–3 above stay: the workflow still spreads, never decides. Backlog stories 25, 29, 30; bug 31 first.

**Version handshake (v5 2026-10-08, v6 2026-10-13, v7 2026-10-21):** `POSTQUALITY_WORKFLOW_VERSION` (main plugin file; the `postquality_workflow_*` helpers are in `includes/pqm-functions.php`) must be bumped whenever `templates/n8n-workflow.json` changes in a way that needs a re-import, together with the hardcoded `workflow_version: N` stamp in the template's Parse Input node **and** the Webhook Trigger's reply (`options.responseData` = `{"ok":true,"workflow_version":N}`, sent on receipt; `rest-reviews-harness.php` checks all three agree). v6 (provisioning entry 3) gave the Webhook Trigger a per-site path: the template carries a second placeholder, `__PQM_WEBHOOK_PATH__`, which `postquality_workflow_json()` fills with `postquality_webhook_path()` (`pqm-execute-<host-slug>`) beside `__PQM_SITE_HOST__`; the guard fails on a literal trigger path. A v5 site that re-imports gets a new production URL to paste; the update notice and the older-version ping message say so, the saved URL is never migrated. v7 (story 2) makes the test ping a round trip: Parse Input's ping item carries `callback_url` (`…/post-quality/v1/ping/<20-char id>`) and `auth_token`, `Ping OK` passes it on to `POST Result to WordPress` (the review's own callback node, header and timeout), and `PostQuality_Admin::sent_ping()` writes the pending id to `postquality_ping` (autoload off, deleted after every ping), waits up to 8 s (filter `postquality_ping_callback_wait`, one read per 500 ms with the Options cache bypassed) for `PostQuality_REST_API::ping_callback()` to mark it `received`, and reports proven / refused (a wrong token: `check_ping_token()` marks the pending ping `refused`) / none — the last two are failed tests on record ("did not pass"). The wait runs only on a current-version reply; an older reply keeps the older-version warning, and a v6 workflow updates in place (entry 9). The update notice (and, on Pro, the Free-variant notice; only the first when both show) carries the page's one primary action: **Re-import the workflow** (`.pqm-reimport`, a delegated click in `pqm-admin.js` that focuses `#pqm-workflow-file`), or, on a site whose workflow the plugin set up or manages (`PostQuality_N8n::managed_blocked()` null, entry 6.9), **Update workflow** (`.pqm-update-workflow`, a delegated click that POSTs `/n8n/workflow` and swaps the block; see `n8n-provisioning.md`). The status block signals it to the page's React islands: the rendered `.pqm-workflow-status .button-primary` (Re-import, Update workflow or Test again, whichever the block renders) is the one source of truth, every swap of the block (`swapWorkflowStatus()` in `pqm-admin.js`, `swapStatusBlock()` in `src/kit/swap-status-block.js`) dispatches `pqm:workflow-status` on `document`, and `src/kit/use-reimport-shown.js` re-reads it, so the setup guide's button and the page's n8n Instance **Connect** turn secondary meanwhile (Connect stays primary inside the guide's Modal); no REST field (2026-10-15, plan-update-notice-primary-action). The workflow reports its version two ways: the trigger's reply to the test ping (v5+; a v1–v4 import answers n8n's default body without a version → recorded as version 0 = "an older version", and the ping never claims the credential was checked), and the `workflow_version` in every `/save-review` callback (0 = untouched). Both write option `postquality_workflow_version_seen` through `postquality_record_workflow_version($version, 'test'|'command')` as `['version', 'via', 'at']`; `postquality_workflow_report()` is the one reader (null when absent; a legacy int from a pre-v5 plugin reads as `{N, command, at 0}`, no migration). A ping records only when the pinged URL is the saved `n8n_webhook_url` (AJAX ping from the n8n Workflow page or a Settings field holding the saved URL; `POST /setup/connect` after it saved the URL). **Forget on serve:** Download (`download_workflow()`) and `GET /workflow` (Import from URL) delete the option, so the page shows "not checked yet" instead of a stale verdict. `PostQuality_Admin::render_workflow_status()` renders the block (`.pqm-workflow-status`: the "update available" notice when the report is older than the template, and the line "version N, checked <when> by a test ping / a command") on page load and as `status_html` in the ping replies; `pqm-admin.js` and the setup dialog (`src/setup/steps.js`) swap it in place. The open page also re-reads the block whenever its tab regains focus (`wp_ajax_postquality_workflow_status` → `PostQuality_Admin::ajax_workflow_status()`, same nonce + `postquality_manage_settings` as the ping, answers `{status_html}`, never pings n8n; a failed read leaves the block), so a download, import from URL or command report made meanwhile shows without a reload. A 2xx from an older workflow comes back with `outdated: true` (`ping_webhook()`, passed on by the AJAX ping and `POST /setup/connect`): connected, but shown as a warning (`.pqm-test-result.is-warning`, the dialog's `Notice status="warning"`; the connect step still ticks). jsdom coverage: `tests/js/workflow-status.test.js`. No automatic ping on page load (each ping is an n8n execution). Skipped: recording the version from a command's dispatch reply (the callback already reports it). The **n8n Workflow** admin page (`postquality-workflow`, `PostQuality_Admin::render_workflow()`) also owns download, import-from-URL, the per-agent request preview, and the connection test; the Settings page keeps only persisted options (all `postquality_settings` fields must stay in the single Settings form — the sanitizer rebuilds the whole array on save).

**Template variant (story 54, 2026-10-12, ADR 0014):** two templates, one version. `templates/n8n-workflow-free.json` is generated by `php bin/derive-free-template.php` from the Pro template (Route Command's paid rules and every node only they reach are removed: 30 → 15 nodes; Parse Input accepts score, review, takeaways, apply) and checked in; `template-guard-harness.php` runs every guard on both files and fails while the Free file differs from a fresh derivation. `postquality_workflow_json()` serves the Free file, the Pro one inside a premium block. Only the Free template states its variant (`workflow_variant: 'free'` in the trigger's ping reply, Parse Input's stamp and the result callback); no variant means Pro, so the Pro template and every older import stay as they were and `POSTQUALITY_WORKFLOW_VERSION` stayed 5 (it is 6 since provisioning entry 3, see the handshake paragraph). `postquality_record_workflow_version($version, $via, $variant)` stores `variant: 'free'` only, and `postquality_workflow_report()` returns it only then; `/save-review` takes an optional `workflow_variant` (enum free/pro, default pro). On the Pro build, a Free template answering a ping is `outdated` (warning, "the Free variant" message) and the status block adds "Your workflow is the Free variant…"; the Free build accepts either template as current.

**Failure contract (workflow v3, bug 31):** the HTTP nodes keep "continue on error", so a failed call reaches the next Code node as an item with `json.error`. Every failure item (empty post caught by a Build or Format Score node, model API error with the provider's own text, unparseable agent output, failed rewrite save via `wp.error`, command without a branch in `Error Fallback`) carries `error: true` + a plain `message` naming what failed; `POST Result to WordPress` sends `error_message: $json.error ? ($json.message || 'The workflow could not complete this command. Check the execution log in n8n.') : ''`, and `save_review_callback` stores a non-empty one as status `error` with `result = {error: message}` (the kit's "Could not complete"). Boundary: only failures with a post and a command the plugin accepts reach `/save-review`; Parse Input rejections (missing `command`/`post_id`, or a command outside the `save-review` `command` enum) cannot be stored by contract and show only in the n8n execution log. The IF `Rewrite Parsed?` routes a failed rewrite parse straight to `Format Rewrite Confirmation`, so `Update WP Post (Rewrite)` never PATCHes the post on failure. Guarded by `tests/harness/template-failure-harness.php` (runs the real node code through Node.js) and the template-contract checks in `rest-reviews-harness.php`.

**Secured, host-agnostic connection (workflow v4, story 35, [ADR 0010](../docs/adr/0010-one-token-authenticates-both-directions.md)):** one token, both directions. `postquality_n8n_headers($settings)` (`includes/pqm-functions.php`) is the one home of the headers every plugin → n8n call sends (Run in `trigger_review_callback()`, cron in `trigger_single_review()`, the test ping): `Content-Type` + `X-PQM-Token: <webhook_token>`. The template's `Webhook Trigger` checks it with n8n Header Auth (credential `Post Quality webhook - __PQM_SITE_HOST__`, header Name field `X-PQM-Token`, Value = the token, picked in the Webhook Trigger only; the Anthropic Header Auth credential goes in the six Claude nodes — the admin copy says which goes where), so the setup needs three credentials; `/save-review` keeps checking the same header on the way back. The payload carries `post_rest_url` = `rest_url(rest_get_route_for_post($post))` (`''` when the post type is not in REST) and `Update WP Post (Rewrite)` PATCHes it as-is — the template assembles no scheme, host or `/wp-json`, so the address is right for any scheme, port, subdirectory and permalink setting. The rewrite itself still needs HTTPS (or environment type `local`): the node signs in with an Application Password, which WordPress core offers only there. `postquality_webhook_url_warning($url)` flags an n8n `/webhook-test/` URL: the ping refuses it before sending, `PostQuality_Admin::save_webhook_url()` (the setup dialog's connect step, story 36) refuses to store it, the Settings save keeps it and adds a `warning` settings error (printed by `render_settings()` via `settings_errors('postquality_settings')`, since core prints them only under Settings → *). Known limitation: a v3 import ignores the header and the new field, so it keeps running but its trigger stays unauthenticated until the owner re-imports. Skipped until a site reports it: token backfill on upgrade, a 403-specific hint on Run.
