**3.0.0 is the first release (2026-10-08), a pre-release test build:** tag `v3.0.0`, GitHub Release with `post-quality-manager-3.0.0.zip` (single root `post-quality-manager/`, `admin/build/` inside), published by `release.yml`. The owner merged release PR #64 before entries 4.2–4.7 and story 15, so 3.0.0 shipped without the version check, the template guard, Plugin Check, translation loading, release notes and the WP 6.6 install test of the zip. No external users had it at that point. Those stories continue and ship in the next release. CI (`.github/workflows/ci.yml`) lints and builds JS, runs the JS unit tests, lints PHP on 8.0 and 8.3, runs the harness sweep (8.3) and runs Plugin Check on the built plugin; `release.yml` (story 4.1, below) is the release path.

`epic-delivery-pipeline` (initiative epic 4) was specced and incepted 2026-10-07 — spec `_bmad-output/initiative-post-quality-manager/spec-delivery-pipeline/` (CAP-1…CAP-7 + `brownfield.md`), 8 stories in its `tickets.toml`. Decisions that bind every story (owner, 2026-10-07):

- release-please on Conventional Commits; the first release is **3.0.0**; it bumps the header `Version`, `PQM_VERSION` and `package.json`, never `PQM_WORKFLOW_VERSION`.
- `GITHUB_TOKEN` only, so release-please PRs trigger no CI: release-please creates the GitHub Release as a **draft**; the release workflow runs the version check, builds and attaches `post-quality-manager-<version>.zip` (root folder `post-quality-manager/`), appends `docs/release-notes/<version>.md` when present, then publishes (tag `v<version>`).
- Release notes are a committed file (backlog story 15, built 2026-10-08; it gates the first public release, entry 4.8). They accumulate in `docs/release-notes/unreleased.md`: a `##` section with no title and no version, because `release.yml` appends it below release-please's `###` changelog. The launch PR (the one that drops `"prerelease": true` and sets `release-as`) renames it to `docs/release-notes/<version>.md`; after the launch the release PR belongs to release-please, so a separate `docs:` PR does the rename once the release PR shows the version, merged before it (a public release with nothing silent still gets a `<version>.md` saying there are no upgrade steps; the next change that needs a line re-creates `unreleased.md`). Pre-releases leave it alone, and the 3.x test builds get no notes file. The Definition of Done (AGENTS.md and `_bmad/custom/bmad-build.toml`) makes a change existing sites meet without being told add one line to it in the same PR; `/release` step 3 stops a public release when `<version>.md` is missing or `unreleased.md` still holds lines.
- Plugin Check runs in CI: report first (4.4), then fixed and blocking (4.5).
- No empty `languages/` folder ships.

Built by story 4.1 (tracer bullet, 2026-10-08):

- `.github/workflows/release.yml`: job `release-please` (push to `main` only, `googleapis/release-please-action@v5`) keeps one release PR open; job `package` runs when `release_created` is true or on a manual dispatch — `npm ci` + `npm run build` on the tag (or the dispatched ref), zips `post-quality-manager/` as `post-quality-manager-<version>.zip` (version from `package.json`) and always uploads it as a workflow artifact; on a release only it attaches the zip, appends `docs/release-notes/<version>.md` when present, and publishes the draft. A manual dispatch never tags or releases.
- `release-please-config.json`: `include-component-in-tag: false` (tags `v<version>`), `draft: true` + `force-tag-creation: true` (without the latter a draft has no tag and the next CHANGELOG would pull the whole history), package `.` with `release-type: node` (`package.json`, `package-lock.json`, `CHANGELOG.md`) and a generic extra file for the plugin main file. `release-as: "3.0.0"` and `bootstrap-sha` `237b1b9` (the first CHANGELOG started after it, owner 2026-10-08) were removed after 3.0.0 shipped; release-please ignores `bootstrap-sha` once a release PR has merged. `.release-please-manifest.json` carries the latest released version; versions now follow the commits.
- Annotations in `post-quality-manager.php`: a `x-release-please-start-version` / `x-release-please-end` block around the header `Version` line (an inline marker would land in the header value WordPress reads), and an inline `// x-release-please-version` on `PQM_VERSION`. `PQM_WORKFLOW_VERSION` carries none.
- **Done after 3.0.0 (2026-10-08):** `release-as` removed, so the next release PR proposes 3.1.0 on a `feat`, 3.0.1 on a `fix`.
- **Pre-releases until the public launch (owner, 2026-10-08).** The repo is private and 3.0.0 had 0 downloads, but its tag stays: every release is a GitHub pre-release until launch. The switch is `"prerelease": true` in the config, but release-please itself only flags suffixed or 0.x versions (`src/manifest.ts`), so it never flagged 3.0.1 or 3.1.0 (the owner re-flagged both by hand, 2026-10-08). The publish step in `release.yml` therefore reads the key with `jq` and passes `--prerelease` itself. A published version number is never reused or re-tagged. A site holding test build 3.0.0 would not be offered a different "real" 3.0.0, because WordPress offers no update for the same version. The launch PR removes `"prerelease": true` and sets `release-as` to the launch version, above the highest one released so far. Entry 4.8 therefore means "first public release", no longer "3.0.0" (renamed 2026-10-08).
- The repo setting "Allow GitHub Actions to create and approve pull requests" must be on for release-please to open its PR. Owner turned it on 2026-10-08; it lets the workflow open its PR, and nothing in the repo approves or merges.
- **Rebase merging only (owner, 2026-10-08).** "Allow merge commits" and "Allow squash merging" are off. GitHub's default merge-commit message carries the PR title in its body, and release-please splits a commit message at every paragraph starting with a Conventional type, so each merged PR's `feat:`/`fix:` was counted twice (once from the branch commit, once from the merge commit). Rebase merging lands the branch commits as they are, with no merge commit. Consequences: commit SHAs change on `main`, so after a merge a local branch reads as unmerged; check that its commits landed, then delete it with `git branch -D`. Every branch commit must follow Conventional Commits, because each one reaches the CHANGELOG.
- **CHANGELOG fix (2026-10-08):** release PR #64 listed `feat(release): release PR and a CI-built plugin zip` twice, because merge commit `a5edbce` (PR #63) predates rebase-only merging. The duplicate line was deleted from `CHANGELOG.md` and from the v3.0.0 release text after the release; release-please never rewrites a released section.
- `ci.yml`'s `admin-build` artifact feeds its Plugin Check job (refactor sweep, entry 7); `release.yml` builds the released commit itself.
- **Refactor sweep (entry 7, 2026-10-08):** the zip upload in `release.yml` carries `overwrite: true` (upload-artifact v4 deletes a same-named artifact before uploading and does not fail when none exists), so re-running a failed `package` job no longer risks an "already exists" failure; that closed the 4.1 deferral.

**Version and PHP-floor guards (story 4.2, built 2026-10-08):** `release-header-harness.php` row 6 fails unless the header `Version`, `PQM_VERSION` and `package.json` agree, printing all three. CI runs it in the harness sweep; `release.yml`'s package job runs the same harness right after checkout ("Versions agree"), so a release out of step fails before build and upload and stays a draft. The CI `php` job is a matrix on 8.0 and 8.3: both lint every plugin file, only 8.3 runs the sweep. Ceiling: `php -l` on 8.0 catches 8.1 syntax, not 8.1-only functions; Plugin Check covers those. `package-lock.json` is not checked.

**Template guard (story 4.3, built 2026-10-08):** `tests/harness/template-guard-harness.php`, run by the CI sweep, fails naming the cause when `templates/n8n-workflow.json` is invalid JSON, carries a placeholder outside `FILLED_PLACEHOLDERS` (mirrors the `str_replace()` in `pqm_workflow_json()`; adding a placeholder means updating both) or lacks one listed there, names a literal host outside `ALLOWED_HOSTS` (`api.anthropic.com`; a new AI provider extends it), contains `localhost` or an IPv4 address, has top-level keys beyond a bare export, a node `id` other than `pqm-node-N`, a `webhookId`, or a credential block with anything but `name`, or has a Code node whose `jsCode` Node.js cannot compile (inside an `AsyncFunction` wrapper, never run). Version-handshake agreement stays in `rest-reviews-harness.php`; its literal-URL and placeholder rows moved to this guard in the refactor sweep (entry 7), so the template rules live in one harness.

**Plugin Check (story 4.4, built 2026-10-08):** the `Plugin Check` job of `ci.yml` runs `wordpress/plugin-check-action` (pinned by SHA, v1.1.9) on every push and PR against the built `post-quality-manager/` folder, all categories. Since the refactor sweep (entry 7) it runs after the build job (`needs: build`) on the downloaded `admin-build` artifact instead of rebuilding; `plugin-check.yml` is gone, and the PR check keeps its name because GitHub names it after the job. **Blocking since story 4.5 (built 2026-10-08):** any Plugin Check error fails CI; warnings never do (the action fails on errors only, unless `strict`, which is off). `ignore-codes: no_plugin_readme` until backlog story 38 writes `readme.txt` and removes it (owner, 2026-10-08). Table names in queries are bound with `%i` (WordPress 6.2+); composed queries whose fragments are already prepared carry a precise `phpcs:ignore … -- reason`. Accepted warnings: direct DB queries and no caching on the plugin's own table, the missing `languages/` folder and `load_plugin_textdomain()` (both until story 38). Triage in entry 5's plan. A report-only check belongs on the step's `continue-on-error`, never the job's (a job-level one still shows a red check on the PR).

**Translations (story 4.6, built 2026-10-08):** header `Domain Path: /languages` and `pqm_load_textdomain()` on `init` (registers the folder; WordPress 6.7+ loads just in time, so nothing loads early). The React bundle reads the same folder via `wp_set_script_translations()`. No `languages/` is tracked, so none ships. Test fixtures for de_DE live in `tests/i18n/` (a `.l10n.php` file and a handle-named `-pqm-app.json`, both hand-written; README there has the site check); `release-header-harness.php` fails if a fixture string disappears from the sources. Once story 38 lists the plugin, translate.wordpress.org language packs replace a bundled folder, and Plugin Check's "load_plugin_textdomain discouraged" warning (entry 4.5) can be resolved by dropping the call.
