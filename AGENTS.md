## Post Quality Manager

WordPress plugin for professional bloggers in any niche: it triggers Claude agents (review, rewrite, takeaways, sources, SEO, audit) through an n8n workflow and stores the results in a WP Admin dashboard. PHP 8.1+ / WordPress 6.6+ (REST API, Options API, WP-Cron); the Dashboard and Post Reviews are React app pages on `@wordpress/components`, Settings and n8n Workflow use vanilla JS (`admin/js/pqm-admin.js`, no jQuery), and the n8n Workflow page also mounts two React islands, the setup dialog (`src/setup/`) and the n8n Instance section (`src/n8n-connection/`); the edit screen of posts carries the Post Quality meta box, a React root from a second build entry (`src/meta-box/`). Work is delivered with the BMad Method (ADR 0004): tickets and plans live in `_bmad-output/`, the skills in `.claude/skills/bmad-*`.

## Policy

- Never commit to `main`; branches `feat/`, `fix/`, `chore/`; Conventional Commits (`feat(admin): add bulk action button`); draft PR for anything touching 3+ files. Sole exception (owner, 2026-10-01): right after a story PR merges, the one-line `chore(tickets)` status flip of that story's plan may be committed directly to main — nothing else ever is.
- Commits, pushes and pull requests need no go (owner, 2026-10-29): the agent commits on its feature branch when it judges the work ready, pushes it (`git push https://github.com/vincentheimann/post-quality-manager.git <branch>`) and opens the PR (`gh pr create --repo vincentheimann/post-quality-manager`). Merging a PR stays the owner's, always.
- Never delete or rename files, change the DB schema or file hierarchy, or add a Composer dependency without asking first. Reading, listing, and creating new classes, functions or admin pages need no permission.
- Plans before code: anything beyond a small change goes through `bmad-build`'s plan checkpoint (`_bmad/custom/bmad-build.toml` routes >100 lines, >3 files, or any schema / REST / template change to the "full" route). If something goes sideways mid-build, stop and re-plan; don't keep pushing.
- Bug reports: find the root cause and fix it without hand-holding; no symptom patches, no temporary fixes.
- AI prompts in the n8n workflow stay niche-agnostic — universal pillars Structure, Readability, Engagement, Credibility; niche tailoring comes from user settings (Blog Profile, brand voice), never from code (`memory/lessons.md` 2026-03-27).
- Read `docs/brand.md` before writing any admin UI text, label or copy; read `docs/user-paths.md` before any product or UX decision.
- Versions belong to release-please: the `Version:` header, `POSTQUALITY_VERSION` and `package.json` carry its markers and are never bumped by hand; merging its release PR tags and publishes the CI-built zip, and every release stays a pre-release until the public launch (`"prerelease": true` in `release-please-config.json`).

## Where things are

- `post-quality-manager/` — the distributable plugin: `admin/class-pqm-admin.php` (admin pages, Settings API, the two AJAX handlers), `admin/class-pqm-meta-box.php` (the post editor's meta box: registration for posts and `postquality_view_reviews`, its script on `post.php`/`post-new.php`), `admin/build/` (compiled React app, two entries, `index.js` and `meta-box.js`; the kit's rules ship in `style-index.css`, which the meta box loads too; git-ignored, built by CI), `admin/js/pqm-admin.js` (vanilla JS; its REST calls go through one `[data-pqm-post]` click handler — the element names the route, `X-WP-Nonce` — beside the two AJAX handlers) + `admin/css/`, `includes/` (DB, REST API `post-quality/v1`, cron, and `class-pqm-n8n.php`, the n8n API client: probe, provisioning, rollback, adoption, update, rotation; it owns the options `postquality_n8n_api`, `postquality_n8n_setup`, `postquality_n8n_leftovers` and `postquality_n8n_provisioning` (the provisioning lock), kept beside `postquality_settings`, never inside it), `templates/n8n-workflow.json` (canonical workflow template, `__PQM_*__` placeholders filled by `PostQuality_Admin::download_workflow()`), `post-quality-manager.php` (initialises the Freemius SDK, `postquality_fs()`, before anything else), `vendor/freemius/` (the SDK at a tagged release, committed unmodified; plugin deletion runs `PostQuality_Activator::uninstall()` through its `after_uninstall` hook, so there is no `uninstall.php`). React sources live in `src/` (`dashboard/`, `post-reviews/`, `setup/`, `n8n-connection/`, `meta-box/`, shared `kit/`). The workflow calls the Claude API directly from n8n Code/HTTP nodes.
- `n8n/workflow-diagram.md` — Mermaid overview of webhook → n8n → Claude → WordPress.
- `_bmad-output/initiative-post-quality-manager/` — the product initiative: requirements (UV1–UV7 from `docs/user-paths.md`, O1–O7 owner requests), epic envelopes in `tickets.toml`; `_bmad-output/backlog/` — standalone tickets. Git is the ticket store; `uv run _bmad/method/scripts/tickets.py status` / `next` read them.
- `_bmad/` — BMad runtime and config; team overrides in `_bmad/custom/*.toml` (committed), personal ones in `*.user.toml` (ignored).
- `docs/adr/` — why we decided (immutable, supersede never rewrite; `/adr`); `docs/user-paths.md` — the EBM prioritization tool (`/prioritize`); `docs/brand.md` — copy rules.
- `memory/` — what is true now: `MEMORY.md` index, one file per durable fact, `lessons.md` the self-correction log whose rules override your defaults. Read at session start; update in the same change that makes a fact true.
- `.claude/skills/` — BMad skills (`bmad`, `bmad-build`, `bmad-spec`, `bmad-ticket`, `bmad-review`, `bmad-code-review`, `bmad-retrospective`, `bmad-project-context`, `bmad-customize`, `bmad-walkthrough`, `bmad-ux`, `bmad-correct-course`; `bmod-*` are module records) plus project skills `/adr`, `/prioritize`, `/release`, `/lcm`.
- `.github/workflows/ci.yml` (JS lint, unit tests and build; PHP lint and harness sweep on 8.1 and 8.3; Plugin Check on the built artifact) and `release.yml` (release-please → CI-built zip → GitHub Release); `docs/release-notes/unreleased.md` holds the lines `/release` moves into `<version>.md` at launch.

## Running and verifying

- `php -l <file>` on every touched PHP file (PHP 8.3 CLI installed via winget; use the full path in a stale shell); `node --check` on every touched JS file.
- CLI regression harnesses live in `tests/harness/` (plain PHP + WP stubs, no WP install): run them all (`for f in tests/harness/*.php; do php "$f" || break; done`) after touching gate, quota, or settings code, and add or extend one whenever a story's plan carries an I/O & Edge-Case Matrix. Shared includes live in `tests/harness/lib/` (`wp-stubs.php`: the runner, the WP classes and the common stubs, every declaration guarded so a harness's own stub declared before the require wins) and are never run alone. The n8n API is covered by four harnesses by concern (`n8n-client-harness.php`, `n8n-provisioning-harness.php`, `n8n-adoption-harness.php`, `n8n-managed-harness.php`) over one shared world, `lib/n8n-world.php` (the n8n stubs, the plugin load, the route registration, every constant and builder, `key_leak_scan()`), which never runs alone either. Real WP Admin behavior is still verified manually (loading and error states included) and with REST calls (200, correct JSON, `permission_callback`). An agent runs the WP-CLI side itself on a Local site (build install, options, a REST call per role, the webhook captured on 127.0.0.1, cron, `debug.log`): `docs/local-verification.md`, entry point `bin/local-wp.py` (story 9). One harness there is not PHP: `local-wp-harness.py` (Python, Windows only, run by hand with `python -I` after touching `bin/local-wp.py` or `bin/webhook-capture.py`); neither the loop above nor CI runs it.
- JS unit tests live in `tests/js/` (Jest + jsdom, run by `wp-scripts test-unit-jest` on the repo's `jest.config.cjs`; since chore 103 Jest and its WordPress presets are the repo's own devDependencies, nothing that ships): `npm run test:unit` after touching `post-quality-manager/admin/js/`, and add or extend a test when a plan's matrix has rows only a browser can show.
- When a REST route or the webhook payload changes, check `post-quality-manager/templates/n8n-workflow.json` for a matching change, and vice versa. Never put site-specific values in the template.
- BMad scripts run with `uv run` (`uv` 0.11+ installed); never run a workflow source file directly — `bmad-build`'s `SKILL.md` renders it first.
- Definition of Done: KISS; `php -l` / `node --check` clean; every harness in `tests/harness/` and `npm run test:unit` green; no WP debug errors or warnings; REST endpoints answer correctly with permissions; UI loading/error states handled; a change existing sites meet without being told (a new default, a new permission, a removed screen, a workflow re-import) adds one line to `docs/release-notes/unreleased.md` in the same PR; durable facts updated in `memory/`, significant decisions recorded via `/adr`, `docs/user-paths.md` adjusted when Unrealized Value became Current Value. Ask "would a staff engineer approve this?" before presenting.
- Report a PR's CI state from `gh pr checks <n> --repo vincentheimann/post-quality-manager` (the check runs the owner sees), never from workflow-run conclusions; to make a CI finding non-blocking, put `continue-on-error` on the reporting step, not the job (`memory/lessons.md` 2026-10-08).

## Conventions that differ from defaults

- Prefix every name the plugin defines in code (story 88, 2026-10-26; `tests/harness/prefix-harness.php` enumerates them): classes `PostQuality_`, functions, hooks, nonces, actions, the option group and query args `postquality_`, constants `POSTQUALITY_`, page slugs and script/style handles `postquality-`, JS globals `postquality…` camel case. Stored names (options, user meta, capabilities, the cron hook `postquality_cron_review_posts` and schedule `postquality_weekly`, the `postquality_reviews` table, the `postquality_settings[…]` form fields) carry `postquality_` too since story 91 (2026-10-26): the old `pqm_` names live only in `PostQuality_Activator::LEGACY_NAMES`, read by the one-time upgrade `migrate_stored_names()` (first thing on `init` and at activation) and by `uninstall()`, which removes both prefixes — never read them anywhere else; `X-PQM-Token`, the REST namespace, the `WP_Error` codes in REST responses (`pqm_forbidden`, `pqm_feature_gated`…), CSS classes, DOM ids, `data-pqm-*`, element expandos (`el.pqmBusy`…), the per-site webhook path prefix `pqm-execute-`, the template placeholders, `metadata.pqmInsert` and file names keep `pqm`. Use WP core APIs (`get_option`, `$wpdb` abstractions) over raw SQL; sanitize (`sanitize_text_field`) and escape (`esc_html`, `esc_attr`) everything; nonces on every form and AJAX request; `permission_callback` on every REST route.
- Native WP admin components and classes (`.wrap`, `.notice`, `.button-primary`); PHP templates and JS-built markup carry no inline styles — add a class in the page's stylesheet instead. The one exception is a value computed at runtime (a tooltip position, a `width: n%` score bar), which stays inline.
- The Settings page is one Settings-API form, Roles tab included, whose `sanitize_settings()` rebuilds the whole array; the n8n Workflow page is form-free — its page-local save is a single-key merge-save (`save_webhook_url()` behind `POST /setup/connect`), never a second form, and REST writes bypass `sanitize_settings()`, so they sanitize in place: a new REST route declares `type` only in `args` and sanitizes inside the callback (story 36 precedent; `memory/lessons.md` 2026-10-05).
- Save is the commit point: never gate an in-form, not-yet-persisted change behind `confirm()`. A preset is a read-only choice resolved from code; Custom is the one editable path and stays visible (`memory/lessons.md` 2026-10-07).
- Pro code carries Freemius build markers (ADR 0014): paid PHP lives in `*__premium_only` functions or in files on the `@fs_premium_only` header list, and every caller sits in `if ( postquality_fs()->is__premium_only() ) { … }` with nothing else in the condition, no `else` and no assignment from a premium call outside it; `bin/build-free.php` and `tests/harness/free-build-harness.php` prove the Free build. After editing `templates/n8n-workflow.json`, run `php bin/derive-free-template.php`.
- Knowledge triad, no duplication: ADR = why, `memory/` = what is true now, skill = recurring how. When a decision reveals a missing practice, propose adopting it instead of designing around its absence (`memory/lessons.md` 2026-07-24).
- After any user correction, append the pattern to `memory/lessons.md` (format documented in the file) and, when it is an agent mistake worth a standing rule, record it with `bmad-project-context record`.

## Known pitfalls

- Disabled form controls don't POST: a sanitizer that reads a disabled knob must fall back to the stored value, not the default, or saving silently resets it (locked temperature/effort knobs, 2026-07-24).
- Workflows imported before 2026-07-22 route `ping` to the Error Fallback; the template-version handshake on the n8n Workflow page is how users learn to re-download.
- The former companion "Post Quality API" plugin was retired 2026-07-23; this plugin's `post-quality/v1/post-score` endpoint is canonical. Do not re-create the standalone plugin.
- Prefer a clarifying question to a large speculative change; use subagents for research and exploration to keep the main context clean.
- Before proposing a change to an external system's settings (GitHub repo or Actions, n8n, hosting), read the current value through its API and confirm the mechanism in the tool's docs or source; never ask to apply a combination the documentation does not state as valid (`memory/lessons.md` 2026-10-08).
